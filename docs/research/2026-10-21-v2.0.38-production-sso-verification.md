The API now uses `https://os.dlabcampus.com/v1`. Production GET `/sso/start` was checked to redirect to `https://os.dlabcampus.com/v1/sso/authorize`; callback registration remains `https://cs.coveedu.com/sso/callback`.

The OS origin is selected with the immutable image SHAs in `deployment.env`, as described in the [release-domain design](../superpowers/specs/2026-10-21-dlab-domain-release-design.md). It overrides the retained legacy value in the private API file for API/judge processes. Older manifests restore the older origin for their pinned image's startup validator; private client, inbound, BFF and Redis secrets were retained.

After the protected deployment completed, new Studio SSO entry was temporarily disabled. Private rollback copies and before/after identity evidence were stored under the server's protected `state/v2.0.38-sso/` directory. The dry run and application each reported exactly one existing managed identity.

The first campus-apply shell invocation consumed subsequent input, so only its audited access operation ran; the remaining configuration/restart commands were then run with their standard input closed and verified to completion.

Only the verified Daechi demo campus is enabled. No new campus or Mapo mapping was created. Normal Mapo accounts were not converted into OS-managed accounts.

## Scope and remaining acceptance

The deployed mapping is `student` → Student; `tutor` → Teacher; `instructor` / `so_staff` / `edu_manager` → Team Lead; `lab_head` → Manager; `hq_admin` → Platform Admin. The additional Team Lead codes and HQ Admin passed automated checks but still need real HQ fixtures for live acceptance.

The new Student correctly sees an empty state because no production class/course has been assigned to that account. Login does not perform teacher assignment or class/course enrollment. Full course/enrollment API synchronization remains outside this release. Additional campuses need explicit verified mappings/enabling; existing Mapo identity linking remains a separate decision. The Supabase browser-session versus reference HttpOnly-cookie requirement still needs the coordination already documented in the SSO runbook.

For an emergency rollback after these staff accounts exist, use the [SSO rollback guidance](../operations/dlab-sso.md#rollback). The retained previous image can recover ordinary application service with its older origin, but it is student-only and cannot be treated as a functional staff-SSO rollback. Preserve managed guards/history and use a compatible staff-aware build for normal SSO recovery.
