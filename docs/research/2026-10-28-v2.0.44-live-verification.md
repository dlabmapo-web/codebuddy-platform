# v2.0.44: live navigation, sample checks and public Turtle verification

Date: 2026-10-28, Asia/Seoul. Release: **v2.0.44**, merged revision
`d096a7ed19fff70d91ae9a4f9d97560b8dc8558a`.

## Deployment and scope

The [release workflow](https://github.com/dlabmapo-web/codebuddy-platform/actions/runs/40611938913)
completed successfully after the required human production approval. Live
Studio, API, judge worker and course GUI service were inspected and were
healthy on the exact released revision. Internal and public production smoke
checks passed.

Signed in sequentially with all five supplied account types: platform admin,
manager, team lead, teacher and student. Visited all **52 visible sidebar
destinations across those roles**, plus selected class, course, student and
coding-workspace details. Repeats bring the retained navigation log to
**81 timing observations**. All audit account sessions were signed out.

This covers visible navigation, not every creation/edit form, dynamic detail,
filter, media type or all 95 source page templates. No curriculum, enrollment,
role, grade or points record was edited. Existing student code was left intact.
Only non-counted Test run actions were used for grading feedback.

These observations support a noticeable improvement on those previously slow
paths. They are **not a controlled before/after cohort or a p95 guarantee**.
The prior audit usually stopped at a changed H1. Current observations generally
wait for a changed main H1, disappearance of skeletons and clearing of
`aria-busy`, then inspect table-row counts and visible state. Client assets and
prefetch/cache state were naturally warm; no cache-busting or simultaneous
load was introduced. Browser-control and screenshot/DOM inspection overhead
are included. Data, network conditions and cache state can differ between days.

The first 22 manager observations used only the heading/skeleton boundary.
Two repeats still had `aria-busy` set while cached rows were visible. Those
samples remain explicitly labelled in the raw log, and were followed by seven
stricter manager observations. The comparison table above uses the final
strict manager repeats. Presence of visible rows does not prove that every
background chart, socket or refetch has settled.

Student Courses took 1.65 / 1.92 s, Overview 2.51 s, class detail 1.38 s and
course outline 1.49 s. These remain perceptible waits. Coding-workspace controls
first appeared at 1.81 s while the editor was still preparing. A separate warm
repeat reached **Test run enabled and editor loading message gone at 2.29 s**.
Those are different boundaries and must not be combined into one improvement
percentage. The earlier workspace result, 2.14 s, used controls-visible only.

Several exploratory waits used a wrong heading, a link whose accessible name
changed when live status connected, or a Monaco textbox locator that was not
stable through the browser bridge. Those waits are not application-latency
samples. The destinations were inspected, selectors corrected, and successful
timed visits retained. No failed page was silently converted to a fast timing.

Console messages included Cloudflare challenge-frame messages and generic
asynchronous-listener messages. This audit does not claim a clean console or
attribute those generic messages to a verified platform exception.

## Turtle startup and contention

The supplied classroom code opened the public workspace. Tests used a synthetic
seven-line program drawing one thick line, with `speed(0)` solely to remove
animation from this startup measurement. Product animation defaults were not
changed. Pen colors alternated so the preceding drawing could not satisfy the
next run's visible-color check.

The first attempt remained at **Waiting for a drawing space** with no colored
frame during its 5.218 s capture window. Broker inspection showed one allocated
guest and two open sessions. Cancelling only this audit's queued request left
one other open session and one allocated guest; this confirmed real contention
for the public pool. Other sessions were not stopped. The slot subsequently
became idle, and further test drawings succeeded.

Once the slot was free, first-visible-frame brackets were:

| Run | New pen color | Click to first visible line, bracket |
| --- | --- | ---: |
| 3 | Blue | 3.020–3.136 s |
| 4 | Green | 3.025–3.158 s |
| 5 | Red | 3.110–3.209 s |

The full **roughly three-second startup wait remains**. The earlier 3.777–4.307 s
observations were not captured with this screenshot method, so this is not a
controlled claim of a particular end-to-end percentage gain. These are fresh
guest reruns under ordinary live conditions, including prior-run teardown and
browser polling/connection. They do not isolate the approximately 0.15 s local
display-readiness component saving.

Frame results are recorded in
[the Turtle timing artifact](assets/2026-10-28-v2.0.44-live-verification/turtle-timings.json).
The first functional red drawing after the queue cleared is excluded from the
timed cohort because a final status locator matched both the run status and
viewer Ready status, preventing that attempt's timing metadata from being
saved. Its raw screenshots remain in the local temporary directory. Three
subsequent attempts retained frame timings before collecting optional statuses.

Frames were captured through CUA's browser screenshot API, cropped to the
observed Drawing region. Offline Pillow analysis looks for at least 100 pixels
of the requested new red, blue or green hue in the observed center-line area.
The explicit channel thresholds and region are recorded in the JSON artifact.
An initial RGB-distance threshold missed the visibly green line because the
display/screenshot colors differed from its literal pen RGB. That diagnostic
and its green screenshot are retained separately; final hue detection was
checked against the actual drawings, without treating the miss as queueing.
Each first-positive frame
is bracketed by the preceding negative screenshot and the positive screenshot's
call timestamps. These bounds include screenshot transport/control overhead;
they do not read hidden application state or the browser canvas pixel API.
This is a small production diagnostic, not the 100-run acceptance cohort.

The completed drawings were visually inspected. Exit returned this audit's
Turtle tab to the classroom-code form and released its grant/session.
