# Team Lead Manual Problem Authoring Design

**Status:** Approved; revised after v1/v2 browser comparison
**Date:** 2026-07-24
**Scope:** Migrate Cove v1 manual programming-problem authoring into the
Cove v2 Content Studio with improved usability, atomic persistence, academy
authorization, course-version publishing, and English/Korean localization.

## 1. Relationship to the content migration design

This specification is the next vertical slice of
`2026-07-24-team-lead-content-migration-design.md`.

The current Cove v2 implementation already supports:

- Academy-owned courses.
- Draft, published, and archived course versions.
- Ordered modules and lectures.
- Module and lecture create, rename, delete, and reorder operations.
- Draft validation and immutable version publishing.
- Copying a published version into the next draft.
- English and Korean translation catalogs with typed keys and extraction
  enforcement.

This slice adds manual programming-exercise authoring inside a lecture.

It also supersedes one permission decision in the original content migration
design:

- `TEAM_LEAD` is the only academy role that creates, edits, deletes, reorders,
  imports, or publishes curriculum content.
- `MANAGER` can read and review draft and published curriculum, but cannot
  mutate it.

Platform `ADMIN`, `TEACHER`, and `STUDENT` do not gain Content Studio authoring
permissions in this slice.

## 2. Goals

A Team Lead can:

1. Open an editable course draft.
2. Choose a lecture and create a Python programming problem.
3. Author all fields available in the Cove v1 manual problem workflow.
4. Add ordered sample and hidden test cases.
5. Add ordered hints.
6. Explicitly save the problem and all children in one transaction.
7. Edit, preview, reorder, and delete the problem while the version is a draft.
8. See the same required-field rules as Cove v1.
9. Receive a warning before leaving with unsaved changes.

A Manager can:

1. Open the same draft or published course version.
2. Open a problem in a read-only review view.
3. See author-visible test cases, including hidden cases.
4. Never receive authoring controls or successfully call authoring procedures.

## 3. Non-goals

This slice does not implement:

- Excel curriculum import.
- AI-feedback rule creation or execution.
- AI-generated problem content.
- Class assignment or course delivery.
- Student submissions or official v2 grading.
- Teacher problem authoring.
- Additional programming languages.
- Rich-text, video, quiz, document, or external-link material types.
- Legacy v1 data transfer.

The existing v1 application and its routes remain unchanged.

## 4. Legacy behavior that must be preserved

The v1 hierarchy is:

```text
Subject -> Stage -> Chapter -> Problem
```

The v2 mapping is:

```text
Course -> CourseModule -> Lecture -> Material -> ProgrammingExercise
```

One v1 Problem becomes one `PROGRAMMING_EXERCISE` Material.

### 4.1 Field mapping

| Cove v1 | Cove v2 | Authoring behavior |
|---|---|---|
| `chapter_id` | `lectureId` | Determined by the lecture from which creation starts |
| `title` | `Material.title` | Required |
| `difficulty` | `ProgrammingExercise.difficulty` | Required: `EASY`, `MEDIUM`, or `HARD` |
| `description` | `ProgrammingExercise.description` | Required rich text |
| `input_format` | `ProgrammingExercise.inputFormat` | Preserved by the service but not exposed by the v1 manual form |
| `output_format` | `ProgrammingExercise.outputFormat` | Preserved by the service but not exposed by the v1 manual form |
| `constraint_text` | `ProgrammingExercise.constraints` | Optional |
| `starter_code` | `ProgrammingExercise.starterCode` | Optional Python source |
| `time_limit_ms` | `ProgrammingExercise.timeLimitMs` | Not shown in the manual form; the server always writes the v1 value of 3,000 ms |
| `memory_limit_mb` | `ProgrammingExercise.memoryLimitMb` | Not shown in the manual form; the server always writes the v1 value of 256 MB |
| `use_ai_feedback` | `ProgrammingExercise.aiFeedbackEnabled` | Optional toggle; rule management remains a later slice |
| `problem_no` | `ProgrammingExercise.legacyProblemNo` | Null for new manual problems |
| Excel `문제키` | `ProgrammingExercise.externalKey` | Generated by the server for manual problems |
| `order_no` | `Material.position` | Unique and ordered within the lecture |
| `test_cases` | `ExerciseTestCase[]` | Ordered input/expected-output pairs saved atomically |
| `problem_hints` | `ExerciseHint[]` | Ordered hint text saved atomically |

The v1 `is_published` problem checkbox does not migrate into the editor.
Publishing is performed on the complete `CourseVersion`, so a class never sees
a partially published hierarchy.

The v1 manual page carries `input_format`, `output_format`, hint trigger
patterns, test visibility, time limits, and memory limits in storage or API
types without exposing author controls for them. V2 does not add controls that
were absent from the v1 manual workflow. Existing values are preserved on
update, while new manual problems use empty format fields, null hint triggers,
the visibility mapping described below, and fixed execution limits.

### 4.2 Required-field compatibility

The new editor must not make a v1-optional field required.

A manual save requires exactly:

- A valid lecture resolved inside the selected academy, course, and version.
- A non-empty problem title.
- A valid difficulty.
- A non-empty problem description after rich-text empty-content normalization.
- At least one test case with a non-empty expected output.

The following remain optional:

- Input format.
- Output format.
- Constraints.
- Starter code.
- Hints.
- AI feedback.

The course publish validator repeats the save requirements. This protects
legacy imports and future mutation paths without changing manual-editor
compatibility.

## 5. Authorization design

Authorization remains permission-based. Role-rank comparisons are prohibited.

### 5.1 Revised Manager permissions

`MANAGER` keeps academy administration permissions, `curriculum.read`, and a
new `curriculum.review` permission for the full Content Studio authoring
projection. It does not receive:

- `curriculum.draft`
- `curriculum.manage`
- `curriculum.publish`
- `exercises.manage`
- `content.import`
- `ai-feedback-rules.manage`

`TEAM_LEAD` keeps all of those content permissions.

`curriculum.read` remains the future released/assigned learner-content
permission. It must not authorize access to draft content or hidden expected
outputs. `curriculum.review` is granted only to Team Lead and Manager.

### 5.2 Procedure permissions

| Procedure category | Permission |
|---|---|
| List Content Studio courses and read full course trees | `curriculum.review` |
| Read an authoring exercise, including hidden cases | `curriculum.review` |
| Create, update, delete, or reorder exercises | `exercises.manage` |
| Validate a course version for review | `curriculum.review` |
| Publish a course version | `curriculum.publish` |

Every service operation validates:

1. Authenticated user identity.
2. Active academy membership.
3. Named permission.
4. Academy ownership of the course.
5. Course ownership of the version.
6. Version ownership of the lecture and material.
7. Draft status for every mutation.

Removing Manager controls in the browser is not an authorization boundary.
NestJS rejects unauthorized Manager mutations independently.

## 6. Information architecture and routes

The course builder continues to show the curriculum tree.

Each lecture displays its ordered programming exercises and, for an editable
Team Lead, an **Add coding problem** action.

```text
New:
/studio/academies/[academyId]/content/courses/[courseId]/versions/[versionId]/lectures/[lectureId]/exercises/new

Edit or review:
/studio/academies/[academyId]/content/courses/[courseId]/versions/[versionId]/lectures/[lectureId]/exercises/[materialId]
```

The URL contains both `lectureId` and `materialId` so the API can reject a valid
material supplied under the wrong parent rather than silently moving it.

Published-version routes use the same review page with all controls removed.
A Team Lead must start the next draft before editing published content.

## 7. Continuous editor experience

The approved layout is a dedicated full-page form with every authoring field
visible in one continuous document. There is no step navigation, accordion,
tab, drawer, or control that hides another part of the form.

```text
+-------------------------------------------------------------+
| Breadcrumbs                         Preview      Save draft  |
+-------------------------------------------------------------+
| Basic information                                           |
| Problem description                                         |
| Conditions and constraints                                  |
| AI feedback                                                  |
| Dark Python starter-code editor                              |
| Answers / test cases                         + Add answer     |
| Hints                                        + Add hint       |
+-------------------------------------------------------------+
```

The author moves through the form by scrolling. On narrow screens the same
order is retained in one column.

### 7.1 Header

The header provides:

- Course, module, and lecture breadcrumbs.
- Create or Edit title.
- Preview action.
- Explicit **Save draft** action for editable Team Leads.
- Read-only badge for Managers and published versions.
- Saved, unsaved, saving, conflict, and failed states.

### 7.2 Form order

The complete form renders in this order:

1. Read-only Course / Module / Lecture context.
2. Required problem title.
3. Required difficulty.
4. Required problem description using the existing Cove `RichEditor`.
5. Optional conditions and constraints.
6. Optional AI-feedback toggle.
7. Optional Python starter code using Monaco with the existing
   `paircode-dark` theme, Python 3 label, line numbers, and the same editor
   ergonomics as v1.
8. Answers/test cases.
9. Hints.

The manual form does not render input format, output format, execution-limit,
test-visibility, or hint-trigger controls because the v1 manual page does not
render them.

### 7.3 Answers / test cases

Each test card contains:

- Input.
- Expected output.
- Stable visible number based on array order.
- Remove action when more than one answer exists.

The form starts with one blank answer. **Add answer** appends another card
directly below the existing cards without navigating or revealing another
surface. The first saved case maps to `SAMPLE`; additional saved cases map to
`HIDDEN` internally. Visibility is not author-editable.

At least one test with an expected output is required to save. Tests use stable
visible numbering based on position.

### 7.4 Hints

Each hint contains:

- Hint content.
- Stable visible number based on array order.
- Remove action.

**Add hint** appends a blank hint card in place. Blank hints are filtered before
saving, matching v1. New manual hints store a null trigger expression. Hints do
not block saving or publishing.

### 7.5 Save readiness

A compact, non-interactive readiness summary may remain sticky on wide screens.
It never hides, changes, or navigates the form. It reflects v1 requirements
rather than introducing new requirements.

```text
Required
[x] Problem title
[x] Difficulty
[ ] Problem description
[ ] At least one answer with expected output
```

Optional fields are not presented as blockers.

### 7.6 Explicit saving and navigation protection

The editor does not autosave.

- Any change marks the form unsaved.
- Save validates the complete client form, then performs one API mutation.
- A successful response replaces local state with the server result and marks
  the form saved.
- Closing, changing route, or reloading while unsaved shows a warning.
- The browser warning is supplemented by an application confirmation dialog
  for Cove-controlled navigation.
- A failed save preserves every local field.

### 7.7 Preview

Preview uses the learner presentation of:

- Title and difficulty.
- Rich problem description.
- Constraints.
- Starter code.
- Sample test cases.
- Hints.

Hidden test cases are excluded from preview. Preview does not execute or grade
code in this slice.

## 8. Shared schemas and contracts

Shared Zod schemas define:

- A manual exercise draft.
- Test-case draft input.
- Hint draft input.
- Exercise create input.
- Exercise update input with concurrency token.
- Exercise read input.
- Exercise delete input.
- Exercise reorder input.

The create and update service commands carry:

- Academy, course, version, and lecture identifiers.
- Material title and required status.
- The v1 manual authoring fields.
- Complete ordered test-case and hint arrays.

The public browser command does not accept author-controlled time or memory
limits. The service writes 3,000 ms and 256 MB. New manual problems use empty
format fields and null hint triggers. Edit state carries existing non-UI format
and trigger values through the save without rendering controls, matching v1.

The update payload also carries `expectedUpdatedAt`. The response includes the
current exercise `updatedAt`.

The academy course contract adds:

- `getExercise`
- `createExercise`
- `updateExercise`
- `deleteExercise`
- `reorderExercises`

All outputs use the existing public content schemas. No Prisma-generated type
crosses the package boundary.

## 9. Persistence and service behavior

### 9.1 Create transaction

`createExercise`:

1. Requires `exercises.manage`.
2. Loads and verifies the editable version and owning lecture.
3. Normalizes and validates the complete input.
4. Allocates the next material position when no position is supplied.
5. Generates a stable server-side `externalKey`.
6. Applies fixed `timeLimitMs: 3000`, `memoryLimitMb: 256`, Python language,
   empty format fields, and null legacy problem number.
7. Creates the Material.
8. Creates the ProgrammingExercise.
9. Creates ordered test cases, mapping the first to Sample and the rest to
   Hidden.
10. Creates ordered hints with null trigger expressions.
11. Writes an audit log with request ID and meaningful after data.
12. Returns the saved exercise or refreshed course tree.

The whole operation runs in one Prisma transaction.

### 9.2 Update transaction

`updateExercise`:

1. Resolves the complete academy-to-material ownership chain.
2. Rejects a non-draft version.
3. Compares `expectedUpdatedAt` with the persisted exercise.
4. Returns an edit conflict if another save happened first.
5. Updates the Material and ProgrammingExercise.
6. Replaces the submitted test-case and hint collections transactionally.
7. Re-packs positions to `1..n`.
8. Writes before/after audit data.
9. Returns the authoritative saved exercise.

Replacement of child collections is acceptable because their identifiers are
not exposed to learner progress or submissions in this slice.

### 9.3 Delete and reorder

- Delete is allowed only in a draft.
- Delete requires explicit confirmation.
- Cascade deletion removes the exercise, tests, and hints with its Material.
- Reordering verifies that submitted IDs exactly match the lecture's current
  material IDs.
- The existing negative-placeholder reorder pattern is reused to avoid unique
  position collisions.
- Each mutation writes an audit record.

### 9.4 Concurrency

If optimistic concurrency fails, the API returns `CONTENT_EDIT_CONFLICT`.

The editor:

- Keeps the unsaved local form.
- Explains that another Team Lead saved a newer version.
- Offers **Reload latest**.
- Does not silently overwrite the newer version.

## 10. Error handling

Stable application errors include:

- `EXERCISE_NOT_FOUND`
- `EXERCISE_TITLE_REQUIRED`
- `EXERCISE_DESCRIPTION_REQUIRED`
- `TEST_CASE_REQUIRED`
- `TEST_CASE_OUTPUT_REQUIRED`
- `CONTENT_EDIT_CONFLICT`
- Existing `COURSE_VERSION_IMMUTABLE`
- Existing `CONTENT_PARENT_MISMATCH`
- Existing `CONTENT_POSITION_CONFLICT`
- Existing `PERMISSION_DENIED`

API error messages are not shown directly. The web application resolves stable
codes through `useErrorText`.

Field validation returns structured issues containing a stable code and field
path. Client copy is localized from those codes.

## 11. Internationalization

The editor copy is grouped under a dedicated exercise subtree or page-scoped
namespace with complete English and Korean catalogs. The implementation must
stay within the existing i18n payload budget.

Requirements:

- No new user-visible English or Korean literals in v2 components.
- Typed translation keys.
- Correct plural forms for tests and hints.
- Stable error-code translations in both locales.
- No unresolved markers or stale catalog keys.
- The existing i18n extraction and payload-budget checks remain green.

The current server-side publish validator returns English `message` strings.
Exercise-related validation introduces stable codes and localized rendering.
A later cleanup may convert older module/lecture validator messages, but this
slice must not add more server-authored display copy.

## 12. Hidden-test security

Cove v1 exposes all judge-case expected outputs to its client-side runner.
That behavior is not migrated.

For v2:

- Authoring procedures may return hidden inputs and outputs only to an active
  academy member with `curriculum.review`.
- Future student content procedures return Sample cases only.
- Future grading runs Hidden cases in trusted server infrastructure.
- Hidden expected outputs are never serialized to a learner browser.
- Preview uses the student-safe projection and therefore excludes Hidden cases.

Official v2 student grading remains outside this slice, but this security
boundary is mandatory now so the authoring API is not reused as a learner API.
The existing Content Studio list/tree procedures must move from
`curriculum.read` to `curriculum.review` before they can return draft structures
or nested exercise data.

## 13. Manager read-only experience

Managers see:

- Content navigation.
- Course list.
- Draft and published version status.
- Complete course trees.
- Problem review pages.
- Sample and Hidden authoring cases.
- A read-only explanation identifying Team Lead as the content owner.

Managers do not see:

- Create-course actions.
- Add module, lecture, or problem actions.
- Rename, delete, or reorder controls.
- Save, import, validate-as-author, or publish actions.
- Editable inputs.

The web application must distinguish:

- `canReviewContent`: derived from `curriculum.review`.
- `canEditCurriculum`: derived from `curriculum.manage`.
- `canManageExercises`: derived from `exercises.manage`.
- `canPublishCurriculum`: derived from `curriculum.publish`.

The current single `canManageContent` helper is insufficient for this
read/write distinction and must be replaced by capability-specific checks.

## 14. Testing strategy

### 14.1 Shared package

- Manager has `curriculum.read` and `curriculum.review`.
- Manager lacks every content mutation permission.
- Team Lead retains all content mutation permissions.
- Teacher and Student lack `curriculum.review`.
- Exercise schemas accept every v1-optional field when empty or omitted.
- Exercise schemas reject missing v1-required fields.
- Browser create/update schemas do not accept author-controlled execution
  limits.
- The web form does not render test-visibility or hint-trigger controls, while
  edit state preserves their existing values.
- Contract inputs require the full ownership chain.

### 14.2 API package

- Team Lead creates a complete exercise transactionally.
- Manager can read but cannot create, update, delete, reorder, or publish.
- Teacher and Student cannot use authoring reads or obtain Hidden cases.
- Cross-academy, cross-course, cross-version, and cross-lecture IDs fail.
- Published versions reject every mutation.
- Test cases and hints save atomically.
- The service always writes 3,000 ms and 256 MB for new manual problems.
- The service maps the first answer to Sample and later answers to Hidden.
- Updating a problem preserves stored non-UI format and hint-trigger values.
- A failed child write rolls back the Material and exercise.
- Manual `externalKey` generation is unique and stable.
- Reorder rejects missing, duplicate, foreign, or extra IDs.
- Optimistic concurrency prevents lost updates.
- Audit records contain academy, actor, request ID, action, target, and
  meaningful before/after data.
- Publish validation preserves the v1-required rule set.

### 14.3 Web package

- Team Lead sees the add and edit workflows.
- Manager sees the review workflow with no writing controls.
- Every authoring field is visible in one continuous form.
- No step navigation, accordion, tab, or drawer hides form content.
- The Monaco editor uses the visible dark v1 theme.
- Inline Add answer and Add hint actions append cards without navigation.
- Completeness reports only the v1-required fields.
- First test defaults to Sample.
- Additional tests map to Hidden without exposing a visibility control.
- Explicit save states render correctly.
- Failed saves retain local input.
- Unsaved navigation warns.
- Preview excludes Hidden test cases.
- English and Korean render without missing keys.
- Accessibility checks cover labels, keyboard navigation, focus movement,
  error summaries, and confirmation dialogs.

### 14.4 End-to-end acceptance

1. A Team Lead opens an Academy A course draft.
2. The Team Lead creates a problem with the same required fields as v1.
3. The Team Lead adds two answers inline; the service maps the first to Sample
   and the second to Hidden.
4. The Team Lead adds an optional hint and enables AI feedback.
5. Save succeeds and reload returns the same data.
6. Editing and reordering survive reload.
7. A Manager reviews the draft and sees no mutation controls.
8. A Manager mutation request is rejected by the API.
9. The version publishes only after required validation passes.
10. The published problem is immutable.
11. Starting the next draft copies the complete problem, tests, and hints.
12. Preview and any future learner projection omit Hidden expected outputs.

## 15. Delivery boundary

This specification is complete when:

- Team Leads can manually create and maintain Python problems with v1 feature
  parity inside course drafts.
- The continuous all-in-one form improves clarity without changing legacy
  authoring fields or required-field semantics.
- Managers have complete read-only review access.
- Content writes are atomic, audited, tenant-scoped, draft-only, and protected
  from lost updates.
- English and Korean are complete.
- Hidden-test answers cannot cross into learner-facing contracts.
- Existing v1 files and behavior remain untouched.

The next specification after this one should cover versioned Excel import into
the same exercise service rather than implement a second persistence path.
